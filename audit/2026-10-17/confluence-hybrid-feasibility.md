# Confluence — 全球ベイクと動的モデルの併用検討

2026-10-17。作者から「各部のCG感が残る。視点ごとに焼いた全球画像とモデルのハイブリッドを試せるか。書庫の下層を参考に」との依頼。本記録は実装調査と比較試作の設計であり、完成プレビューを作成・公開したという意味ではない。

## 結論

試作可能で、現行の操作に適合する。採用候補は**静的な建築・岸・根・遠景をCyclesで全球ベイクし、水面・円盤・触れて起こる波・動く影を実時間描画する構成**。白と青の配色、3か所から見回す操作、原典に沿った地形、現在の波の安定性、観測説明を維持する。

現行 `confluence-v10-20261017-engine.js` の眼点は以下で固定されている。

| 視点 | 眼点 x,y,z |
| --- | --- |
| 床の切れ目 | -1.65, 2.23, 1.3 |
| 円盤の真下 | -7.6, 2.23, -8.5 |
| 岸の道 | 11, 2.25, 15 |

`confluence-v9-20261017-viewer.js` はドラッグで向き、ピンチ・ホイールで画角を変更する。場所ボタンで眼点が切り替わり、自由歩行ではない。このため全球画像の中心に眼点を置く条件を満たす。場所間は読み込みと切替にし、画像だけで歩行中の視差を近似しない。

## 書庫の下層から使える構成

`CANON_TEXT.md` ASSET 29、`shoko-v1-w2-app.js`、`shoko-v1-w1-05-hyb-landscape-view.json` と反射のJSON、実際の静止プレート画像を確認した。

- 下層はCyclesの静止プレートと深度に、水と搬送の荷のモデルを重ねる。
- 反射は別に焼く。反射データは水面を鏡にしたscene-linear画像で、動く荷は含まない。
- 背景はAgX適用済みの表示色で、二度トーンマッピングしない。動くモデルとの色・光の整合を個別に扱っている。
- 下層は縦横別の固定構図の透視画像。**360度の全球画像ではない**。Confluenceではこの合成方式を全球へ拡張する。
- 書庫のthree r186は作品固有の例外。Confluenceへライブラリをそのままコピーせず、既存r128で構成する。

リポジトリの旧Confluence v5にも全球の色・深度、鏡側の色・深度を使う実装がある。実装参考にはなるが、旧風景・旧水面を戻す方針ではない。Earth v6には、固定眼点の色と放射距離を使った新しい実装と検証記録がある。いずれも今回のConfluenceで実測済みという扱いにはしない。

## 描画の分担

| 要素 | 方針 |
| --- | --- |
| 白い建築、床、道、岸の起伏、根、葉、残存壁、遠景 | 形状・材質を推敲後、静的な間接光と接地影を含めてCyclesで焼く |
| 全球の深度 | 各方向の放射距離を保存し、水・円盤との前後関係を復元 |
| 水面、タップで起こる波 | 現行v8以後の有界な波の式を基礎に、実時間描画を維持 |
| 円盤 | 立体のまま回転。背景と同じ光・露出・色変換に合わせる |
| 水面への風景の映り込み | 各眼点を水面の下へ鏡映した位置から、反射用の全球色・深度を別に焼く。通常の背景を上下反転するだけでは済ませない |
| 円盤の映り込み | 反射用の背景へ円盤だけを描画して合成 |
| 円盤が落とす動く影 | 最終画像に固定して焼き込まない。背景深度から位置を復元して影を加える。直接光だけを遮る補助パスを比較し、間接光まで黒く潰す処理を避ける |
| 水際の細い境界 | 深度の精度で足りなければ、簡略化した縁・根の遮蔽モデルを残す |
| タップ説明 | 軽量な判定形状、または観測対象IDの全球マップ。説明UIは現行の共通Liquid Glassを維持 |

静的な水際の影は水面用の事前遮蔽データへ分離する。波の色・反射・影・地形との境界が別々の風景に見えないことが最優先。反射の外れや過去の波の縞模様を再導入しない。

## 焼く前に直すこと

「CG感」は描画方式だけで決まらない。コード上でも、道はほぼ一定の断面、根は規則的に生成され、葉はカード、素材の変化は反復ノイズに依存する。これらをそのまま画像化しても形の均一さは残る。

- 道の端を一定の鋭い線から、土に沈む肩・わずかな欠け・堆積の連続へ変える。通行面そのものを無意味に荒らさない。
- 根の太さ、分岐、地面への潜り込みを局所的に調整し、浮いた接合や同じ形の繰返しを減らす。
- 根元、壁と床、残存壁の足元の接地を形状と間接光で成立させる。
- 石、樹皮、湿った岸の粗さと色むらを異なる尺度で作る。輪郭を隠すために一律に汚し・霧を追加しない。
- 白と青の採用色は維持し、遠景の霞と近景の階調・細部で距離を出す。

## 最初の比較試作

「岸の道」一視点から始める。道・根・水際・風景の反射を同時に評価できるため。現行版と同じ眼点・画角で比較し、同じプレビュー内で方式を切り替えられるようにする。

1. 岸の道の近景モデルと材質を整え、静的な全球色・深度と、鏡映位置からの全球色・深度を制作。
2. 現行の水・円盤・タップ波を合成。反射と動く影を合わせる。
3. 前後左右、空、足元、全球の継ぎ目、画角40〜85度、縦横画面を確認。葉と水際の深度輪郭も拡大して確認する。
4. タップ対象と実際の見た目の一致、停止・再開、場所切替中の古い画像の混入を確認。
5. 見た目が改善した場合に床の切れ目・円盤の真下へ展開。最終の一式保存ZIPを別場所で起動検証し、操作可能なプレビューを提示する。

現行版を一枚の静止画にして比べるだけでは、Cyclesによる改善もハイブリッドの成立も検証したことにしない。

## 負荷と解像度の予算

現行は静的な風景も通常画面と水の反射の両方で描く。これを画像へ置き換えることで、静的な形状・照明の実時間計算を減らせる見込み。ただし水と円盤の実時間描画は残る。速度・消費電力の改善量は新しい試作で測定する。

旧v5の1眼点分はRGBA8換算で、4096×2048の色32 MiB、8192×4096の深度128 MiB、2048×1024の反射色8 MiB、4096×2048の反射深度32 MiB、計200 MiBだった。サイズはコードの読み込み寸法から計算した値で、端末全体の実測メモリではない。この割当をそのまま戻さない。

初期比較の候補は、通常色・深度を4096×2048、反射色・深度を2048×1024。色4 bytes/pixel、深度をWebGL2のRG8に16bitで詰める仮定なら計60 MiB。軽量側は各辺半分で15 MiB。表示画像とHDR反射の符号化、深度の近遠精度を実装時に検証する。これは追加の光・影パス、ミップ、描画バッファ、デコード中の一時メモリ、ブラウザキャッシュを含まない予算案。圧縮ファイルの通信量とも別。

全3視点を同時にGPU保持せず、現在の視点を優先して交換する。全球画像は全周に画素を配るので、4Kで近くの根や拡大時の細部が不足する場合は、眼点を共通にした正面の高精細画像を追加する方式も比較する。無条件に8Kへ上げない。
